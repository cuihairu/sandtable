# Sandtable 项目计划

> **Sandtable --- A configuration-driven simulation and experimentation
> framework for game systems.**
>
> 中文定位：**面向游戏系统的配置驱动仿真与实验框架 / 游戏数字沙盘**

------------------------------------------------------------------------

## 1. 项目定位

### 1.1 核心目标

Sandtable 不是单纯的战斗模拟器，也不是单纯的经济流图工具。

它的目标是提供一个可以把游戏系统放入"数字沙盘"中长期推演的框架：

``` text
Game Configuration
        ↓
Game Model
        ↓
Players / Actors
        ↓
Combat / Economy / Progression
        ↓
Simulation
        ↓
Metrics / KPI
        ↓
Experiment
        ↓
Parameter Analysis / Optimization
        ↓
Balance Recommendation
```

它要回答的问题是：

> 如果调整某个游戏参数，让大量不同类型的玩家运行 7 天、30
> 天甚至更长时间，整个游戏系统最终会发生什么变化？

例如：

-   某角色攻击力从 100 调整到 95/105 后，胜率如何变化？
-   掉落金币增加 10% 后，30 天经济会不会通胀？
-   升级成本曲线变化后，玩家第 7/14/30 天的战力分布如何变化？
-   Casual/Core/Whale 玩家是否出现明显不同的成长路径？
-   哪些参数对目标 KPI 最敏感？
-   在满足多个 KPI 约束的情况下，哪些参数组合更合理？

------------------------------------------------------------------------

# 2. 产品边界

## 2.1 Sandtable 做什么

第一阶段重点：

-   配置驱动的游戏模型
-   长期时间推进
-   玩家/Actor 模拟
-   战斗
-   资源经济
-   成长系统
-   玩家分群
-   KPI / Metrics
-   Monte Carlo
-   参数 Sweep
-   实验结果比较
-   参数敏感性分析
-   可复现实验
-   HTML/JSON/CSV/Parquet 报告

后续：

-   参数优化
-   Bayesian Optimization
-   Evolutionary Optimization
-   Pareto Optimization
-   真实游戏引擎 Adapter
-   CI 平衡回归
-   Web UI
-   可视化系统图
-   策划工作流

## 2.2 第一阶段明确不做

避免项目一开始失控，MVP 不做：

-   通用 MMORPG 引擎
-   游戏服务器运行时
-   完整 Machinations 克隆
-   Unity/Unreal/Godot 编辑器
-   LLM 玩家
-   强化学习玩家
-   复杂行为树编辑器
-   在线 SaaS
-   多人协作平台
-   复杂自动寻优 UI

核心原则：

> **先把 Simulation Kernel 和 Experiment Loop 做正确，再做产品界面。**

# 3. 核心概念模型

Sandtable 的核心不是功能列表，而是以下六个模型概念：

``` text
Model
Actor
System
Scenario
Metric
Experiment
```

------------------------------------------------------------------------

## 3.1 Model --- 游戏世界模型

Model 描述"游戏是什么"。

``` text
World
├── Clock
├── Entities
├── State
├── Systems
├── Rules
└── Event Queue
```

Model 不应该绑定某一款具体游戏。

例如：

``` yaml
stats:
  warrior.attack: 100
  warrior.defense: 80

monsters:
  slime:
    hp: 500
    defense: 30
```

------------------------------------------------------------------------

## 3.2 Actor --- 玩家行为模型

Actor 描述"谁在玩，以及如何行动"。

Actor 不是简单的一组属性，而是：

``` text
Actor
├── State
├── Attributes
├── Goals
├── Strategy
├── Schedule
├── Preferences
└── Decision Model
```

第一阶段采用简单可配置行为模型。

例如：

``` yaml
actor:
  type: casual

  activity:
    sessions_per_day: 2
    session_duration: 20m

  behavior:
    dungeon_probability: 0.7
    upgrade_probability: 0.2
    explore_probability: 0.1
```

后续再扩展复杂行为模型。

------------------------------------------------------------------------

## 3.3 Cohort --- 玩家分群

建议将 Cohort 与 Actor 分开。

``` text
Cohort
├── Casual
├── Core
├── Whale
├── Returning
└── Churn Risk
```

Cohort 是一类玩家的统计/行为模型。

Actor 是模拟运行过程中产生的具体玩家实例。

``` text
Cohort
   ↓ spawn
Actors
   ↓ behavior
World
   ↓
Metrics
   ↓
Cohort Analysis
```

------------------------------------------------------------------------

## 3.4 System --- 游戏系统

System 描述游戏系统如何改变世界状态。

典型系统：

``` text
Combat
Economy
Progression
Inventory
Reward
Activity
Daily Reset
```

系统之间允许形成反馈环：

``` text
Combat
  ↓
Reward
  ↓
Economy
  ↓
Progression
  ↓
Power
  ↓
Combat
```

这正是 Sandtable 与单场战斗模拟器的重要区别。

------------------------------------------------------------------------

## 3.5 Scenario --- 仿真场景

Scenario 描述"一次实验如何运行"。

例如：

``` yaml
scenario:
  duration: 30d
  population: 10000

  population_mix:
    casual: 0.60
    core: 0.30
    whale: 0.10

  seed: 123456
```

Model 描述游戏本身。

Scenario 描述实验环境。

二者必须分离。

------------------------------------------------------------------------

## 3.6 Metric --- 指标

Metric 描述"如何判断系统运行得好不好"。

支持：

``` text
Scalar
Time Series
Distribution
Histogram
Percentile
Cohort
Correlation
```

例如：

``` yaml
targets:
  combat.win_rate:
    min: 0.48
    max: 0.52

  economy.inflation:
    max: 0.05

  progression.day_7_power:
    min: 10000
    max: 15000
```

Metric 不只是仿真结束后的统计值，而是系统目标的一部分。

------------------------------------------------------------------------

## 3.7 Experiment --- 实验

Experiment 描述"如何改变参数并比较结果"。

``` text
Parameter Space
       ↓
Simulation
       ↓
Metrics
       ↓
Constraints
       ↓
Ranking
       ↓
Recommendation
```

第一阶段支持：

-   Grid Search
-   Random Search
-   Monte Carlo
-   Parameter Sweep

后续支持：

-   Latin Hypercube
-   Bayesian Optimization
-   Evolutionary Optimization
-   Pareto Optimization

# 4. Simulation Kernel

这是整个项目最重要的技术资产。

建议设计成：

``` text
World
├── Clock
├── RNG
├── Entity Store
├── State
├── Systems
└── Event Queue
```

Simulation Engine：

``` text
Simulation
    ↓
Event / Tick
    ↓
System Update
    ↓
State Change
    ↓
Event
    ↓
Metric
```

------------------------------------------------------------------------

## 4.1 时间模型

必须同时考虑两种执行方式。

### Fixed Tick

适合：

-   战斗
-   实时状态
-   DPS
-   Buff/Debuff
-   冷却

例如：

``` text
0ms
50ms
100ms
150ms
...
```

### Discrete Event

适合：

-   登录
-   战斗开始
-   奖励
-   升级
-   每日结算
-   离线收益

例如：

``` text
Day 1 09:00 Login
Day 1 09:03 Battle
Day 1 09:05 Reward
Day 1 09:06 Upgrade
Day 1 10:00 Logout
```

两者不应该互相排斥。

------------------------------------------------------------------------

# 5. Deterministic RNG

可复现性属于核心能力，而不是附加功能。

一次实验至少应该由：

``` text
seed
model_version
config_hash
scenario_hash
experiment_id
```

共同确定。

建议提供独立 RNG Stream：

``` text
RNG
├── combat
├── loot
├── economy
├── behavior
└── world
```

目标：

> 修改一个参数后，尽可能让两次实验使用可比较的随机路径，从而降低 RNG
> 噪声。

------------------------------------------------------------------------

# 6. 配置与脚本模型

## 6.1 不要让 YAML 成为编程语言

配置负责描述数据和简单规则：

``` yaml
stats:
  attack: 100
  defense: 80

formula:
  damage: "max(1, attack - defense)"
```

复杂行为应该通过脚本/扩展机制完成。

核心原则：

> **配置描述数据，代码/脚本描述复杂行为。**

------------------------------------------------------------------------

## 6.2 第一阶段配置格式

推荐：

-   YAML：主要用于人类编辑
-   JSON：机器交换
-   TOML：CLI/工程配置可选

第一阶段优先：

> YAML + JSON

------------------------------------------------------------------------

## 6.3 Formula Engine

不要直接执行任意代码。

建议实现受控表达式 AST：

``` text
Arithmetic
Comparison
Boolean
Min / Max
Clamp
Random
Lookup
Conditional
```

例如：

``` text
damage = max(1, attack * skill_ratio - defense)
```

后续可以增加：

-   函数
-   表查找
-   Curve
-   Piecewise
-   Distribution

------------------------------------------------------------------------

# 7. 技术栈

## 7.1 Core

### Rust

推荐 Rust 作为 Sandtable 的核心实现语言。

原因：

-   高性能
-   内存安全
-   非常适合大量模拟
-   并行计算能力强
-   CLI 生态成熟
-   WASM 支持优秀
-   可以嵌入其他工具
-   适合最终运行数十万/百万级 simulation

核心要求：

``` text
Deterministic
Headless
Parallel
Embeddable
Testable
```

``` text

90 / 140
...
110 / 200
```

## Random Search

用于高维参数空间。

# 13. KPI / Target System

KPI 应该支持：

``` text
Minimum
Maximum
Range
Target
Tolerance
Weight
Hard Constraint
Soft Constraint
```

例如：

``` yaml
targets:

  - metric: combat.win_rate
    min: 0.48
    max: 0.52
    type: hard

  - metric: economy.inflation
    max: 0.05
    type: hard

  - metric: progression.day_7_power
    target: 12000
    tolerance: 0.10
    type: soft
```

最终可以形成：

``` text
Candidate A
    Win Rate      PASS
    Inflation     FAIL
    D7 Power      PASS

Candidate B
    Win Rate      PASS
    Inflation     PASS
    D7 Power      PASS
```

# 14. 参数敏感性分析

这是一个非常重要的能力。

目标不是只告诉用户：

> 最优值是 97。

而是告诉用户：

``` text
Parameter Importance

warrior.attack       0.72
monster.defense      0.51
gold.reward          0.34
upgrade_cost         0.18
```

进一步：

``` text
warrior.attack
    ↓
Win Rate        +0.8%
D7 Power        +1.4%
Inflation       +0.1%
```

这样策划才能知道：

> 哪些参数真正值得调整。

------------------------------------------------------------------------

# 15. Recommendation

最终输出应该从：

``` text
Simulation Result
```

逐步升级到：

``` text
Recommendation
```

例如：

``` text
Current:
warrior.attack = 100

Recommended:
96 ~ 101

Reason:
- Win Rate currently exceeds target
- D7 progression remains within target
- Economy impact is minimal

Confidence:
High
```

第一阶段不需要复杂 AI。

先使用：

-   参数 Sweep
-   Constraint
-   Score
-   Sensitivity

就足够。

# 22. 关键设计原则

## 原则 1：Simulation First

不要先做漂亮 UI。

------------------------------------------------------------------------

## 原则 2：Deterministic First

实验必须可以复现。

------------------------------------------------------------------------

## 原则 3：Configuration Driven

游戏数据应该尽可能与引擎解耦。

------------------------------------------------------------------------

## 原则 4：Engine Agnostic

不要绑定 Unity / Unreal / Godot。

------------------------------------------------------------------------

## 原则 5：Experiment First-Class

Experiment 不是 CLI 外面的脚本，而是核心模型。

------------------------------------------------------------------------

## 原则 6：Population First

不要只模拟一个"平均玩家"。

------------------------------------------------------------------------

## 原则 7：Long-Term First

不要只模拟一场战斗。

至少要能够：

``` text
Day 1 → Day 30
```

------------------------------------------------------------------------

## 原则 8：Measure Before Optimize

先把：

``` text
Simulation
Metrics
Experiment
Sensitivity
```

做好，再做复杂优化算法。

``` text
      Combat      Economy      Growth
        │            │            │
        └────────────┼────────────┘
                     ↓
                  Metrics
                     ↓
                   KPI
                     ↓
              Parameter Analysis
                     ↓
               Recommendation
```

最终用户体验应该是：

``` text
1. 修改游戏配置
2. 定义实验
3. 运行 10,000 / 100,000 个玩家
4. 推进 7 / 30 / 90 天
5. 查看 KPI
6. 比较参数
7. 找到敏感参数
8. 获得推荐参数
```

而不是：

``` text
写代码
↓
跑脚本
↓
自己处理 CSV
↓
自己 Excel 分析
```

中文：

> **Sandtable
> 是一个面向游戏系统的配置驱动仿真与实验框架，用于长期模拟玩家、战斗、经济和成长系统，并通过实验与指标分析辅助游戏平衡。**

# 25. 项目最终愿景

Sandtable 最终应该成为：

> **游戏开发者的数字沙盘。**

它不是告诉策划：

> "这个技能 DPS 是 12,532。"

而是帮助回答：

> "把这个参数改掉以后，整个游戏运行 30 天会发生什么？"

从：

``` text
Combat Simulation
```

升级到：

``` text
Game System Simulation
```

再进一步：

``` text
Game System Experimentation
```

最终形成：

``` text
Simulation
+
Experiment
+
Measurement
+
Optimization
```

这才是 Sandtable 的核心价值。

# 26. MVP 验收标准

第一版不以"功能多少"为验收标准，而以以下闭环是否成立为标准：

``` text
配置
 ↓
建立世界
 ↓
生成玩家群体
 ↓
玩家执行行为
 ↓
战斗
 ↓
获得资源
 ↓
成长
 ↓
继续活动
 ↓
时间推进
 ↓
运行 30 天
 ↓
收集 KPI
 ↓
改变参数
 ↓
重新运行
 ↓
比较结果
 ↓
给出参数建议
```

如果这个闭环可以稳定、可复现、可并行地运行：

> **Sandtable MVP 成立。**
