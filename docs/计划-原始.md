# Sandtable Project Plan


> **Sandtable --- A configuration-driven simulation and experimentation
> framework for game systems.**

------------------------------------------------------------------------

## 1. Positioning

### 1.1 Core Goal

Sandtable is neither a pure combat simulator nor a pure economy flow-charting tool.

Its goal is to provide a framework where game systems can be placed into a "digital sandbox" and iterated over long horizons:

``` text
Game Configuration
        ↓
Game Model
        ↓
Players / Actors
        ↓
Combat / Economy / Progression
        ↓
Simulation
        ↓
Metrics / KPI
        ↓
Experiment
        ↓
Parameter Analysis / Optimization
        ↓
Balance Recommendation
```

The question it has to answer is:

> If one game parameter is adjusted and a large population of different player types runs for 7 days, 30
> days or even longer, what ultimately changes across the whole game system?

For example:

-   When a character's attack moves from 100 to 95/105, how does the win rate change?
-   After dropped gold grows by 10%, does the 30-day economy inflate?
-   Once the upgrade-cost curve changes, how does the player power distribution on days 7/14/30 change?
-   Do Casual/Core/Whale players end up on visibly different progression paths?
-   Which parameters are most sensitive to the target KPIs?
-   Under several KPI constraints at once, which parameter combination is more reasonable?

# 3. Core Concept Model

The core of Sandtable is not a feature list but the following six model concepts:

``` text
Model
Actor
System
Scenario
Metric
Experiment
```

------------------------------------------------------------------------

## 3.1 Model --- The Game World Model

Model describes "what the game is".

``` text
World
├── Clock
├── Entities
├── State
├── Systems
├── Rules
└── Event Queue
```

Model should not be bound to any one specific game.

For example:

``` yaml
stats:
  warrior.attack: 100
  warrior.defense: 80

monsters:
  slime:
    hp: 500
    defense: 30
```

------------------------------------------------------------------------

## 3.2 Actor --- The Player Behavior Model

Actor describes "who is playing, and how they act".

An Actor is not a flat set of attributes, but:

``` text
Actor
├── State
├── Attributes
├── Goals
├── Strategy
├── Schedule
├── Preferences
└── Decision Model
```

Phase 1 adopts a simple, configurable behavior model.

For example:

``` yaml
actor:
  type: casual

  activity:
    sessions_per_day: 2
    session_duration: 20m

  behavior:
    dungeon_probability: 0.7
    upgrade_probability: 0.2
    explore_probability: 0.1
```

Complex behavior models come later.

------------------------------------------------------------------------

## 3.3 Cohort --- Player Cohorts

Cohort is recommended to be kept separate from Actor.

``` text
Cohort
├── Casual
├── Core
├── Whale
├── Returning
└── Churn Risk
```

A Cohort is the statistical/behavioral model of one class of players.

An Actor is a concrete player instance produced during a simulation run.

``` text
Cohort
   ↓ spawn
Actors
   ↓ behavior
World
   ↓
Metrics
   ↓
Cohort Analysis
```

------------------------------------------------------------------------

## 3.4 System --- Game Systems

A System describes how a game system changes world state.

Typical systems:

``` text
Combat
Economy
Progression
Inventory
Reward
Activity
Daily Reset
```

Systems are allowed to form feedback loops:

``` text
Combat
  ↓
Reward
  ↓
Economy
  ↓
Progression
  ↓
Power
  ↓
Combat
```

This is exactly what separates Sandtable from a single-battle simulator.

------------------------------------------------------------------------

## 3.5 Scenario --- The Simulation Scenario

Scenario describes "how one experiment runs".

For example:

``` yaml
scenario:
  duration: 30d
  population: 10000

  population_mix:
    casual: 0.60
    core: 0.30
    whale: 0.10

  seed: 123456
```

Model describes the game itself.

Scenario describes the experiment environment.

The two must be separated.

------------------------------------------------------------------------

## 3.6 Metric --- Metrics

Metric describes "how to judge whether the system runs well".

Supported:

``` text
Scalar
Time Series
Distribution
Histogram
Percentile
Cohort
Correlation
```

For example:

``` yaml
targets:
  combat.win_rate:
    min: 0.48
    max: 0.52

  economy.inflation:
    max: 0.05

  progression.day_7_power:
    min: 10000
    max: 15000
```

A Metric is not only a statistic computed after the simulation ends; it is part of the system's targets.

------------------------------------------------------------------------

## 3.7 Experiment --- Experiments

Experiment describes "how to change parameters and compare results".

``` text
Parameter Space
       ↓
Simulation
       ↓
Metrics
       ↓
Constraints
       ↓
Ranking
       ↓
Recommendation
```

Supported in phase 1:

-   Grid Search
-   Random Search
-   Monte Carlo
-   Parameter Sweep

Supported later:

-   Latin Hypercube
-   Bayesian Optimization
-   Evolutionary Optimization
-   Pareto Optimization

# 4. Simulation Kernel

This is the single most important technical asset of the whole project.

Recommended design:

``` text
World
├── Clock
├── RNG
├── Entity Store
├── State
├── Systems
└── Event Queue
```

Simulation Engine：

``` text
Simulation
    ↓
Event / Tick
    ↓
System Update
    ↓
State Change
    ↓
Event
    ↓
Metric
```

------------------------------------------------------------------------

## 4.1 Time Model

Both execution modes have to be considered.

### Fixed Tick

Suited to:

-   Combat
-   Real-time state
-   DPS
-   Buff/Debuff
-   Cooldowns

For example:

``` text
0ms
50ms
100ms
150ms
...
```

### Discrete Event

Suited to:

-   Login
-   Battle start
-   Rewards
-   Level-ups
-   Daily settlement
-   Offline income

For example:

``` text
Day 1 09:00 Login
Day 1 09:03 Battle
Day 1 09:05 Reward
Day 1 09:06 Upgrade
Day 1 10:00 Logout
```

The two must not exclude each other.

# 5. Deterministic RNG

Reproducibility is a core capability, not an add-on feature.

One experiment should be determined at least by:

``` text
seed
model_version
config_hash
scenario_hash
experiment_id
```

taken together.

Independent RNG streams are recommended:

``` text
RNG
├── combat
├── loot
├── economy
├── behavior
└── world
```

Goal:

> After one parameter changes, keep the random paths of two runs comparable wherever possible, so that RNG
> noise is reduced.

# 6. Configuration and Scripting Model

## 6.1 Do Not Turn YAML into a Programming Language

Configuration is responsible for describing data and simple rules:

``` yaml
stats:
  attack: 100
  defense: 80

formula:
  damage: "max(1, attack - defense)"
```

Complex behavior belongs in scripts / extension mechanisms.

Core principle:

> **Configuration describes data; code/scripts describe complex behavior.**

------------------------------------------------------------------------

## 6.2 Phase 1 Configuration Formats

Recommended:

-   YAML: mainly for human editing
-   JSON: machine exchange
-   TOML: optional for CLI/project configuration

Phase 1 priority:

> YAML + JSON

------------------------------------------------------------------------

## 6.3 Formula Engine

Do not execute arbitrary code directly.

A controlled expression AST is recommended:

``` text
Arithmetic
Comparison
Boolean
Min / Max
Clamp
Random
Lookup
Conditional
```

For example:

``` text
damage = max(1, attack * skill_ratio - defense)
```

Possible additions later:

-   Functions
-   Table lookup
-   Curve
-   Piecewise
-   Distribution

------------------------------------------------------------------------

# 7. Tech Stack

## 7.1 Core

### Rust

Rust is recommended as the core implementation language of Sandtable.

Reasons:

-   High performance
-   Memory safety
-   Very well suited to large-scale simulation
-   Strong parallel computation
-   Mature CLI ecosystem
-   Excellent WASM support
-   Embeddable in other tools
-   Suited to eventually running hundreds of thousands / millions of simulations

Core requirements:

``` text
Deterministic
Headless
Parallel
Embeddable
Testable
```

``` yaml
    min: 100
    max: 200

```

Generated automatically:

``` text
90 / 100
90 / 120
90 / 140
...
110 / 200
```

------------------------------------------------------------------------

## Random Search

For high-dimensional parameter spaces.

------------------------------------------------------------------------

## Monte Carlo

Used for:

-   RNG

# 13. KPI / Target System

KPIs should support:

``` text
Minimum
Maximum
Range
Target
Tolerance
Weight
Hard Constraint
Soft Constraint
```

For example:

``` yaml
targets:

  - metric: combat.win_rate
    min: 0.48
    max: 0.52
    type: hard

  - metric: economy.inflation
    max: 0.05
    type: hard

  - metric: progression.day_7_power
    target: 12000
    tolerance: 0.10
    type: soft
```

The result can end up as:

``` text
Candidate A
    Win Rate      PASS
    Inflation     FAIL
    D7 Power      PASS

Candidate B
    Win Rate      PASS
    Inflation     PASS
    D7 Power      PASS
```

------------------------------------------------------------------------

# 14. Parameter Sensitivity Analysis

This is a very important capability.

The goal is not merely to tell the user:

> The optimal value is 97.

but to tell the user:

``` text
Parameter Importance

warrior.attack       0.72
monster.defense      0.51
gold.reward          0.34
upgrade_cost         0.18
```

Further:

``` text
warrior.attack
    ↓
Win Rate        +0.8%
D7 Power        +1.4%
Inflation       +0.1%
```

Only then can designers know:

> which parameters are genuinely worth adjusting.

``` text
Simulation Result
```

up to:

``` text
Recommendation
```

For example:

``` text
Current:

Recommended:
96 ~ 101

Reason:
- Win Rate currently exceeds target
- D7 progression remains within target
- Economy impact is minimal

Confidence:
High
```

Phase 1 needs no complex AI.

Start with:

-   Parameter Sweep
-   Constraint
-   Score
-   Sensitivity

That is enough.

# 22. Key Design Principles

## Principle 1: Simulation First

Do not build a pretty UI first.

------------------------------------------------------------------------

## Principle 2: Deterministic First

Experiments must be reproducible.

------------------------------------------------------------------------

## Principle 3: Configuration Driven

Game data should be decoupled from the engine as much as possible.

------------------------------------------------------------------------

## Principle 4: Engine Agnostic

Do not bind to Unity / Unreal / Godot.

------------------------------------------------------------------------

## Principle 5: Experiment First-Class

Experiment is a core model, not a script outside the CLI.

------------------------------------------------------------------------

## Principle 6: Population First

Do not simulate only one "average player".

------------------------------------------------------------------------

## Principle 7: Long-Term First

Do not simulate only a single battle.

At minimum it must be able to:

``` text
Day 1 → Day 30
```

------------------------------------------------------------------------

## Principle 8: Measure Before Optimize

Get these right first:

``` text
Simulation
Metrics
Experiment
Sensitivity
```

then build the complex optimization algorithms.
