# Sandtable 六项待决策建议

日期：2026-10-30。依据：[2026-10-30-analysis.md](./2026-10-30-analysis.md)、当前 `todo.md` 剩余项及相关实现；仓库 HEAD 为 `6697810df31fd4bb5acef79d7b08cfd5a183b4d8`。

这是供学习和拍板的建议稿，不代表你已经批准实施。“立即执行动作”指采纳后的工作，本轮仅写此文件，没有修改仓库、运行构建或实施这些动作。下文的启动条件是建议新增的管理规则，不是仓库已有的验收结果。

建议整体选择：先把现有本地工具变成可交付、可对账的产品；投入一个真实数据试点；服务器、专用商业工具连接器与新优化算法按证据启动。

## 1）多人协作／服务端形态

**推荐｜当前采用 local-first + 文件交接；保留未来增加轻服务端的可能，暂不建设。**

local-first 指项目和仿真优先在用户电脑上运行；轻服务端指另设一个负责账号、项目版本、评论或任务协调的服务。两者未来可以并存，并非只能永久二选一。

**理由｜**

1. **收益：**现有 `.sandtable` 项目归档和离线报告可以承担“交付一个版本、别人复现和评审”的基本协作，无需先做网络产品。依据：`todo.md:404`、`crates/sandtable-cli/src/project.rs`。
2. **成本：**轻服务端即使只存文件，也新增账号权限、部署、备份、版本兼容和故障处理，不能仅按“加几个接口”估算。
3. **风险：**文件共享容易互相覆盖；先用“一次只有一人维护主版本、其他人另存分支、合并前审查”的规则控制。归档字节稳定不等于能对 ZIP 内部做安全的自动语义合并。
4. **取舍：**暂时牺牲同时编辑、在线评论和集中权限，换取更快验证实际工作流。若团队频繁卡在版本交接，再做服务端才有明确目标。禁止游戏服务器运行时，不等于禁止项目协作后端。

**立即执行动作｜**

- 制定文件协作约定：主版本负责人；每次交接记录项目版本、父版本、作者、变更说明；结果带配置 hash、seed、程序版本。
- 普通用户用版本文件夹交接；熟悉 Git 的团队可将可读配置纳入 Git，归档作为交付件。网盘同名文件避免多人同时覆盖。
- 用两人跑一次“复制项目→分别改参数→评审→确定主版本→复现”的演练，记录冲突和人工耗时。
- **重启条件：**实际团队确认文件交接持续妨碍工作，且能明确所需能力、服务维护人及数据存放位置。首个服务只做不可变项目版本、下载和必要权限；远程计算另行决策。

**明确不做／延后什么｜**本期不做实时共同编辑、自动配置合并、账号系统、云端仿真集群；不将文件交接描述为已经完成多人在线协作。该 todo 可记录“方向已决”，不能据此勾选原在线协作验收。

## 2）数据分析面：真实数据与指标映射

**推荐｜优先立一个真实游戏、一个版本、一个成熟玩家批次的小试点；先对账，后拟合。复用已实现的 Python 和 MCP 入口，不重做 loader。**

“映射”就是写清楚：业务报表里的哪个数字，与仿真的哪个数字，按什么公式、时间和人群比较。“校准”才是随后调整模型参数使两边更接近。

**理由｜**

1. **收益：**这项直接验证“模型能否帮助真实数值决策”，比增加平台接口更能消除产品有效性的不确定性。数据分析面和真实案例二期共用这道数据闸门。
2. **成本：**入口、脚本执行和起步模板已存在（`todo.md:434`）；新增工作主要是数据提取、清洗、口径确认和真实验收。不要再次按完整分析平台报价。
3. **风险：**同名不等义最危险。注册留存、日活、永久流失、日人均收入、全程人均产出不能混用，否则再好的拟合也会给出误导结论。
4. **风险：**现有“±10% + 留存观测值至少 0.9”是仓内验收规则，不能自动变成所有真实游戏的标准。真实留存为 40% 时，即使模型准确复现也会被现实现判 FAIL；必须把业务健康目标与拟合精度分开确认。
5. **收益与边界：**保留一段未参与拟合的数据，可以发现“只记住历史”的过拟合。仿真随机误差区间只能说明重复仿真的波动，不能替代真实数据抽样误差或未来预测可信度。

**立即执行动作｜**

1. **发出最小接收清单。**由业务数据负责人提供 `cohort_day.csv`、`economy_day.csv`、`meta.yaml`；按需提供抽卡样本。原始数据留在本地，先选固定版本、固定地区／渠道和足够成熟的玩家批次。`meta.yaml` 明确时区、观察窗口、人口分母、批次定义、币种／单位、胜负定义、流失判定及数据版本。无需把明细上传给助手。
2. **制作并共同确认指标映射表。**每项记录源表列、筛选范围、分子／分母、时间轴、缺失处理、对应内核字段、可比／不可比原因和确认人；保存映射版本及文件校验值。映射表至少包含下面这些判断。

| 指标 | 推荐真实侧算法与对齐规则 | 当前能力及需补条件 |
| --- | --- | --- |
| D3／D7 留存 | 同一第 1 天活跃人群中，第 n 天仍活跃人数 ÷ 第 1 天人数；明确与业务“注册后第几天”的偏移 | 内核以 day-1 cohort 为分母，D1 恒为 1。`active_players` 不天然等于所需分母；原接收列不足时补批次基数，未成熟批次不参与。先算运行级 anchors，当前 MCP 不提供留存逐日 series |
| 胜率 | 同范围有效胜场数之和 ÷ 有效战斗数之和；明确平局、退出、重试算不算 | 可接运行级或逐日胜率；不能把各组胜率简单平均。无战斗日应标不可比 |
| 金币全程人均产出 | 窗口内匹配来源的金币发放总量 ÷ 对齐后的初始玩家数 | `gold_per_player = gold_earned_total / players`；不是期末余额，也不是除以每日活跃人数之和 |
| 金币日产出／消耗 | 当天匹配范围的产出／消耗 ÷ 当天活跃人数 | MCP 的 `gold_per_player` series 对应日产出人均；日消耗先用经济 Python 模板复核，不假称 MCP 已提供完整经济序列 |
| 流失率 | 窗口内累计被判流失人数 ÷ 初始玩家数，且流失规则与模型一致 | 运行级 `churn_rate` 对应累计流失，不是当天新增流失率；不能无条件用 1−D7 替代。无法对齐则 UNMAPPED |
| 战力／掉落／抽卡 | 分别需同定义的快照分布、可分来源掉落金额、同机制的首次命中抽数 | `power_p50` 取最后可用快照，不保证任何结束日都有快照；没有同义业务量就不映射。抽卡未命中样本不能直接丢弃，否则均值有偏 |

3. **先验证数据，再运行工具。**Python／DuckDB 将原始表转换为标准 CSV 和明确的整数日轴，检查重复行、缺日、负数、零分母及加总一致性。MCP 接收显式 `mapping`，不会自动根据 `meta.yaml` 理解所有业务语义；运行级观测须先聚合后填入 anchors。样例以正分母、可解释观测开始；真实零值另列绝对误差规则，不能加一个小数伪造为正值。
4. **人工核对少量锚点。**先用业务已有报表复算一个留存点、一个胜率点和一天经济数据，再调用 `sandtable_calibrate` 生成差异报告。Python 用来预处理和独立复核；现有经济模板按日期排序编号，缺日时会压缩日轴，且零值处理需检查，不能未经审查用于真实验收。默认模板 `days.csv` 还是第 0 次仿真，不可当多次均值。
5. **冻结验收，再启动拟合。**将 ±10% 作为讨论起点，按数据噪声约定各指标相对／绝对误差；0.9 健康底线单列，必要的规则调整经确认后另开实施任务，本轮不改。先冻结结构、只选少量有业务解释的数值参数及范围，再复用 sweep／optimize／RF。
6. **留出验证。**可用前约 70% 时间窗拟合、尾段验证；比较时必须让仿真延续到对应尾段，不能把尾段重新编号成新开服第 1 天。留存还需保证批次成熟、不把同一观测同时用于拟合和验收。若只有一个成熟批次的少数 D3／D7 点，应另留独立批次或后续数据，不能硬称已有时间留出。

**明确不做／延后什么｜**不接全量线上数据管道，不建数据仓库，不新增没有观测对象的 KPI；不拿公开案例或仿真自洽样本代替真实验收。缺数据时可完成清单、映射模板和机制检查，但不宣称校准成功；如实保留 UNMAPPED 和未达标项。既有设计把 loader 排为下一步的文字已落后于实现，后续应统一口径。

## 3）MSI 安装器是否 fork WiX

**推荐｜当前不 fork Tauri 的整份 WiX 模板；保持现有安装链，优先验收安装和使用。安装界面品牌图可作为独立小优化。**

这里的 fork 指复制并长期维护上游安装模板，不必然是 fork 整个 WiX 工具项目。

**理由｜**

1. **收益：**避免为局部图标效果引入整份模板的长期维护；当前 exe、应用列表和开始菜单已有图标链记录，核心演示不依赖剩余两处外观。
2. **成本：**自定义模板后，每次相关 Tauri 升级都要核对上游变化、重测安装／升级／卸载。仓内记载模板约 381 行，维护范围明显大于改一个属性。
3. **风险：**本机缺 Windows／WiX 验证条件；仓内记载 MSI 构建失败可能影响整组 nightly 发布。应优先完成 Windows/macOS 真机交互验收。
4. **证据边界：**上一轮关于桌面快捷方式及 `.msi` 文件本体的描述来自仓内历史核查，尚非本轮真机结论；尤其“添加 File 表 Type=2 图标行即可改变 MSI 本体图标”不应作为已证实方案。文件本体的显示还涉及系统文件关联，需单独验证。

**立即执行动作｜**

- 记录“暂不承担自定义模板维护，原图标缺口延后”，保留原验收范围，不能勾成已修复。
- 用现有产物完成安装、启动、原生文件对话框和核心流程走查，截图确认实际有问题的图标位置及系统版本。
- 若仅需安装界面带品牌，评估 `bannerPath`／`dialogImagePath` 配置；它们是安装 UI 图片，不解决快捷方式或 MSI 文件本体图标。官方支持这些配置和自定义 `template`，见 [Tauri WixConfig](https://v2.tauri.app/reference/config/#wixconfig)。
- **重启条件：**真机确认影响分发或用户识别，存在明确验收截图、有维护负责人和 Windows 回归环境；先检查局部定制或上游修复是否可行，再决定是否整模板 fork。

**明确不做／延后什么｜**本期不复制整模板，不承诺 MSI 文件本体一定显示自定义图标；品牌图片作为可选美化，不替代原两处缺口的验收。

## 4）Web API 做不做、什么时候做

**推荐｜现在不做面向网络的 Web API；明确调用方和远程任务后再做窄接口。**

API 是程序调用入口；已有 CLI、Python、MCP、WASM 和桌面桥，均不意味着必须再加 HTTP 服务。浏览器有页面也不等于需要后端。

**理由｜**

1. **收益：**现有本地入口已能支撑演示、脚本编排和数据对账，新增 Web API 暂无已确认的增量使用者。
2. **成本：**仿真是可能耗时的计算任务，网络化通常涉及任务队列、进度、取消、结果保留和资源限额，不能只包装一个同步路由。
3. **风险：**API 一旦被外部调用，就产生兼容性承诺；场景、指标和错误口径未通过真实试点前冻结，会放大后续改动成本。
4. **边界：**协作文件服务和远程仿真服务是两种需求。未来只需要集中存项目时，可仅做项目管理接口，不必把仿真一起搬上服务器。

**立即执行动作｜**整理现有调用方式及产物协议；用真实工作流判断是否仍有“必须跨机器调用”的任务。**启动闸门：**至少有一个明确调用方，能给出完整输入／输出案例、任务规模、运行地点、数据边界、部署维护人和服务目标，并说明现有入口为何不够。届时先提交小范围接口契约；远程仿真首版限提交任务、状态／取消、结果获取，复用内核，使用固定任务 ID 和配置身份。

**明确不做／延后什么｜**不预建公共 API、云端 Python 执行、SDK 全家桶、计费和多租户平台；不把“协作选轻服务端”当作远程仿真 API 自动获批。todo 保留方向性待办，触发时另立项。

## 5）GP 优化是否立项

**推荐｜不立 GP 实现项目；先在实际优化任务上评估现有 RF，必要时才立小型对照试验。**

RF（随机森林）和 GP（高斯过程）都是用已跑结果估算未跑候选的“代理模型”；代理不是仿真真值。GP 在某些连续平滑、小样本问题中可能值得尝试，是否适合本项目要靠对照。

**理由｜**

1. **收益：**现有 sweep、进化寻优和 RF 已能工作；先了解误差和节省的真实仿真次数，才能知道新算法解决什么问题。依据：`todo.md:461`、`crates/sandtable-core/src/surrogate.rs`。
2. **成本：**GP 增加核函数、噪声与超参选择、数值稳定处理及跨平台验证负担；还要核对现有 WASM、确定性和依赖约束。
3. **风险：**换算法无法修正错误指标、无效参数范围或与真实业务脱节的模型。当前首先缺真实任务和 RF 不足证据。
4. **统计边界：**RF 树间 min/max 只是树间分歧，不能当统计置信区间。GP 的不确定性也受建模假设约束，不能直接标成业务预测保障。

**立即执行动作｜**

- 在第一个真实优化任务上固定参数范围、指标和总仿真预算，保留未参与训练的候选，比较 RF 与简单扫描／随机候选策略。
- 记录留出误差、推荐候选经真仿真后的达标率，以及达到同等目标所需的仿真次数和总耗时；多组种子复核，不只挑最好的一次。
- **立项闸门：**RF 确实反复漏掉有价值候选或耗费不可接受预算；任务有适合 GP 的结构；能预先定义可接受收益。可将“同预算下稳定改善达标率，或达到同目标至少节省约 20% 仿真次数”作为待确认的试验门槛，不能说已证明能达到。
- 满足闸门后，先离线对照 GP 和 RF；收益成立再讨论生产接入及依赖方案。所有最终推荐仍回到真仿真复验。

**明确不做／延后什么｜**不先替换 RF、不先引入生产线性代数依赖、不立全套贝叶斯优化平台；代理预测不混入真实观测层。基准可随真实试点做，尚无任务时不为验证 GP 而造一个项目。

## 6）商业分析工具接口：JMP／Power BI 等

**推荐｜做稳定的文件交付，暂不做专用连接器和自动发布；有实际使用团队后，只选其首要工具做一个导入试点。**

JMP 更偏统计分析，Power BI 更偏团队报表；“让它们能读取文件”和“Sandtable 自动操控、刷新、发布它们”是两档工作。

**理由｜**

1. **收益：**已有 XLSX 工作簿、CSV／JSON 等产物和字段字典，可作为最小交付基础；统一字段与版本同时服务多个工具。依据：`todo.md:400–403`、`crates/sandtable-cli/src/workbook.rs`。
2. **成本：**专用集成需要对应软件环境、真实使用者和持续兼容验证；现有环境不足以宣称 JMP／Power BI 导入、脚本自动化或发布已通过。
3. **风险：**表能导入不代表报表正确。必须处理运行身份、参数、玩家批次、逐日明细的关联粒度，避免多表连接重复计数，避免把第 0 次运行的 CSV 当成多次平均。
4. **运营成本：**Power BI 服务自动刷新本地来源可能需要网关配置和维护；这超出一次文件导入。见 [Microsoft 本地 Desktop 文件刷新说明](https://learn.microsoft.com/en-us/power-bi/connect-data/refresh-desktop-file-local-drive)。
5. **范围：**仓内还包含 Origin／Tableau 待办；没有消费需求时同时支持全部工具会分散验证资源。先维护通用数据契约最划算。

**立即执行动作｜**

- 整理一份现有产物的交付清单：表粒度、主键／关联键、字段字典、空值、单位、版本和配置身份；明确每个文件的 replicate 范围。已有项复用，缺项单列，不重做导出系统。
- 提供一个小型、无真实个人明细的示例包及通用导入步骤；导入说明与“已在目标软件实测”分开标记。
- **启动闸门：**确定工具及版本、实际分析问题、消费人、授权环境和刷新频率。首轮以“导入成功、三项关键数值与源产物一致、更新一版仍能重读”为验收；在目标软件实测后才宣布兼容。
- 手动导入持续造成重复劳动后，再决定 JMP 脚本化或 Power BI 刷新；优先复用目标工具已有文件导入能力，再判断是否需要连接器。

**明确不做／延后什么｜**不同时建 JMP、Origin、Power BI、Tableau 专用适配层；不代购许可证，不预建企业报表发布、网关部署或持续同步。文件可交付不能视为原商业工具自动化 todo 全部完成。

## 总执行顺序

1. **先拍板边界：**采纳 ①本地优先、③暂不 fork、④暂不做 Web API、⑤暂不立 GP 实现、⑥文件优先；这些决定用于控制投入，不等于对应功能已完成。
2. **做可交付基线：**整理本地演示／复现说明、文件交接规则、现有导出字典；优先完成 Windows/macOS 人工交互验收，确认 MSI 实际问题。真实数据尚未到位时，这些工作可独立推进。
3. **主投入放在②：**接收真实数据→确认映射→手算对账→工具差异报告→确认验收规则→少量参数拟合→独立留出验证。数据没到就停在接收和映射准备，不拿合成数据冒充成果。
4. **沿试点收集需求证据：**观察两人交接是否困难；如有实际商业工具使用者，做一个文件导入试点；真实寻优任务同时记录 RF 基准。三者都按真实任务推进，不为填 todo 人为扩范围。
5. **最后按触发条件分别重开项目：**文件协作不足才做轻服务端；有远程调用方才做 Web API；RF 对照显示不足才试 GP；反复手动导入形成负担才做商业工具自动化；真机图标问题值得长期维护才重评 WiX 定制。这些不是必须依次全部建设的路线图。

执行含义：近期主要资源用于真实数据有效性和已有产品交付质量；其余项目以明确触发条件管理。后续若更新 todo，应分别记录“决策已定”“环境／数据待到位”“功能已实现”“实际验收已通过”，不要将四种状态合并为一个完成勾。
