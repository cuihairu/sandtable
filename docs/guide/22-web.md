# 22 · Web

The Phase 6 deliverable (document [Roadmap](./18-roadmap.md)): **"Try in your browser"** — open the page, change the configuration, run a small-to-medium simulation locally, charts come out directly, zero install, data never leaves the browser.

## Form factor

`apps/web`: a Vite + React + TS frontend consuming the `sandtable-wasm` binding artifacts (a `file:` dependency, not via the npm registry). Zero charting libraries — per-day curves are hand-drawn SVG in the frontend (the same visual discipline as the CLI `report` subcommand: no CDN, no external resources, no JS charting runtime).

Page capabilities (current increment):

- Preset configurations (minimal RPG / Pokémon case) load in one click, or import a local `.yaml` configuration file and edit it directly in the editor;
- `replicates` 1–8, running `run_simulation` locally;
- KPI cards (D3/D7 retention, daily win rate, total churn rate, gold per player, power per player) and `config_hash`;
- Per-day curves (daily active / daily win rate / gold stock / level-up count);
- Cohort table (level, gold, power, churn for casual / core / whale);
- **SQL query panel (DuckDB-Wasm)**: the simulation artifact is loaded into the in-memory table `days`, and arbitrary SQL runs locally (result table + one-click line chart of the per-day numeric columns). Zero external requests — worker and wasm are both bundled locally through vite `?url`, not via a CDN; the mvp single-threaded build is loaded on demand (39 MB of assets, downloaded only when the query is opened);
- **Result export**: `days.csv` (replicate 1, byte-for-byte identical to what the CLI's `simulate --out` writes to disk), `report.json` (structurally isomorphic, with `results` identical value by value), and `days.parquet` (the same per-day data written to Parquet through DuckDB `COPY ... (FORMAT PARQUET)`, zero new dependencies), all downloadable in one click — drop them into one directory and `sandtable report` / `sandtable query` can continue the analysis ([data output](./09-data-output.md) contract). report.json is generated single-sourced in `lib/reportArtifact.ts` (shape locked by node guards, same contract as the CLI's `meta_json`): meta carries only the four environment fields, `results` passes through verbatim, and `config_hash` rides each result entry — environment fields take no part in determinism, so rerunning with the same seed leaves `results` and `days.csv` bit-identical.
- **Project packing and typed-path entry (2026-10-13)**: the toolbar's "Pack project (.sandtable)" packs the two editors' contents + the current results into a `.sandtable` (fflate, manifest v1, entries sorted by path, per-entry sha256 via WebCrypto, archive timestamp fixed at 1980-01-01, the same rules as the CLI's `project pack`), read directly by `sandtable project check` / `unpack`; besides the native dialog (multi-select), the "local result file analysis" panel also has a typed-path entry (single append with de-duplication, views still registered by file stem) — the equivalent route for when the native dialog cannot be automated headlessly, with functionality identical to the duckdb-rs query. Desktop downloads are wired through the shell's `on_download` into `~/Downloads` (same names automatically get a (n) suffix, see [Roadmap Phase 7](./18-roadmap.md));
- **Parameter sweep (grid / Random + recommendation band + joint feasible region)**: the experiment file (three sections: scenario + model + sweep, [document chapter 12](./12-parameter-sweep.md)) is swept locally — through YAML editing or the preset selector (single-axis grid / single-axis random / two-axis grid), driven candidate by candidate by JS (candidate parallelism is unavailable under single-threading; the main thread yields between candidates, so progress can be rendered); it produces a candidates × metrics table (constraint verdicts PASS / BORDERLINE / FAIL, failing candidates annotated and never silently dropped), single-axis charts (grid line / Random scatter, CI95 required, verdicts color-coded, recommendation band and baseline markers), the two-axis joint feasible region matrix (per-target three-color verdicts, sparse Random cells left empty), the OAT sensitivity matrix and the recommendation block — the same source as the CLI's `sweep` / `recommend` (core pure functions); budget gates: candidates × replicates ≤ 200, players × days ≤ 400,000, beyond which users are steered to the CLI.

## Binding discipline

[`sandtable-wasm`](https://github.com/cuihairu/sandtable/tree/main/crates/sandtable-wasm) is a **thin binding**:

- It forwards core only (load → validate → run) and **carries no simulation logic**; the real logic lives in native pure functions (`*_native`), which cargo test covers directly;
- The wasm entry points return **JSON strings** and the frontend calls `JSON.parse` — it does not go through serde-wasm-bindgen's JsValue protocol (measured silent incompatibility with newer wasm-bindgen: to_value produces an empty object; a string is the most stable channel across the wasm ABI);
- `run_simulation` output carries `days_csv` (replicate 1, straight out of `core::export::day_csv`) — the CSV is rendered by Rust, so browser downloads and CLI on-disk writes are **byte-for-byte identical** (locked down by `web_parity`); floats are never reassembled on the JS side;
- The three sweep bindings (`sweep_plan / sweep_candidate / sweep_recommend`) are pure forwarding as well; candidate parallelism (rayon) is unavailable under single-threading, so **JS drives them candidate by candidate**, yielding the main thread between candidates — `replicates` is given uniformly by the plan; candidate / recommend do not each interpret it; recommendation covers a single parameter axis only (an MVP red line, refused the same way as [document chapter 15](./15-recommendation.md)); a sweep cancel stops at candidate-loop boundaries (the main thread yields between candidates, so it works on web and desktop), and after a cancel the finished candidates stay in the table but no recommendation is produced;
- `meta` carries only `schema_version / model_version`; `generated_at_unix / git_sha` are environment fields, injected by the frontend build (`VITE_GIT_SHA`, injected during the CI build; falling back to `unknown` when not injected, the same as the CLI without `SANDTABLE_GIT_SHA`); the binding layer does not fabricate them;
- The ceiling on replicates is 64 (the Web form targets small-to-medium simulations: the 4GB WASM memory cap, single-threaded, [data output](./09-data-output.md)); larger experiments are steered to the CLI / desktop.

### Config write-back / serialization contract (WB-03.07)

Configuration has two channels on the frontend with non-overlapping duties:

- **Human write-back goes through the YAML text layer**: `applyParamEdit(s)` performs token-level replacement, never re-serialization — comments, key order and all unedited structural config (the `damage_model` enum, the `xp_needed` formula, per-tier `tier_table`, loot `tables/rewards/on_victory`, `gacha`, `training`) are preserved byte for byte (locked by workbench tests). `serde` re-serialization drops comments and reorders keys and is **forbidden** as the human write-back channel.
- **The kernel-object channel emits only the hash and the read-back value**: `param_apply` applies via `registry::apply_numeric`, then re-validates (the explicitness contract — e.g. loot must arrive fully configured — is enforced at edit time) and returns `{config_hash, path, value}` — **never YAML**. `config_hash` is the kernel-canonical SHA-256; the YAML text itself never enters the hash.
- Numeric bridges reject structural parameters (duration / formula / structural tables / enum switches) with "该参数不是数值" (not a numeric slot) — structural config can only change through text editing or dedicated structural editors.
- **u64 safe-integer boundary (WB-03.08)**: u64 slots (seed, pity counters) read as JSON numbers while ≤ 2^53−1; values beyond the JS safe-integer range come back as **lossless decimal strings**. Writing an out-of-range value is explicitly rejected by the kernel ("exceeds the safe-integer cap 2^53−1") — neither direction ever rounds silently.

### A/B statistical comparison bridge (WB-03.10/.11/.12)

The A/B comparison input contract and the statistics both live in the kernel; the frontend never recomputes a rival version:

- **Entry** `ab_compare(base_yaml, cand_yaml, metric, results_a_json, results_b_json)`: both arms' YAML plus both arms' **already-run** results arrays (same shape as the `results` field of `run_simulation` — fed back into the kernel, never re-run); the kernel entry point is `core::experiment::compare_arms`.
- **Paired preconditions fail explicitly** (never a silent downgrade): arms with different `base_seed` (CRN pairs by replicate index, so a seed mismatch makes paired diffs meaningless), replicate counts unequal or zero, a metric unavailable in either arm (`unavailable_reason`, no single-arm skipping), or a replicate whose `extract` returns None (never zero-filled). Error channels: unknown metric / results parse failure = `参数错误: `, everything else = `配置错误: `.
- **Statistics come straight out of the kernel's `experiment::compare`**: paired diffs (B_r − A_r), CI95, pooled sd, effect size d, and the verdict (three values decided by the CI sign); the frontend `Comparison` type is isomorphic to the serialization (runtime-locked by contracts).
- **The compared metric** is the first KPI of the design targets (falling back to `win_rate` with none selected); its validity is decided by the kernel's `MetricKey::parse`.

### Binding generation guard (WB-03.13)

After any change to the wasm export surface you must **rebuild both pkgs** before type-checking or running tests: `wasm-pack build crates/sandtable-wasm --target web --release` (browser + tsc) and `--target nodejs --out-dir pkg-node --dev` (node tests). The symptom of a missed rebuild is a runtime `does not provide an export named …`. The **binding generation guard** in contracts automates this discipline: it collects every named import from `sandtable-wasm` across the TS wrappers (the wasm.ts service layer and the worker entry) and checks each name against three faces — the pkg-node runtime exports, the web pkg's JS exports, and its `.d.ts` declarations. A wrapper calling an ungenerated export turns the suite red. pkg / pkg-node are build artifacts and stay out of git.

### Unified error classification and locale display (WB-03.15)

Binding-layer errors speak a **stable channel-prefix contract** (`配置错误: ` / `参数错误: ` / `候选结果序列化失败: `, the same strings as the CLI's stderr), and the display layer unifies them into six classes: **parse failure** is an independent class — the kernel folds YAML parse failures into the `配置错误` channel and arm-results parse failures into the `参数错误` prefix (the channel-prefix contract is untouched), and the display layer upgrades them to a `parse` code on the "parse failed" fact (changing the config and never having parsed are different things); **config / param / serialize** follow their prefixes; **initializing / init failure / run error / budget overrun / missing kernel bridge** go through the execution-side `ExecErrorClass` (init/run/budget/bridge; initializing renders as running, no fabricated progress); **cancel** is not an error — it lives on the state machine as `cancelled/cancelling`. Locale display: `localizeWasmError` maps a recognizable message to a stable error code plus a dictionary template (`errors.*`; templates differ per language, the code is identical), with the raw kernel message preserved verbatim in `detail` for triage; the task list body goes through `execErrorText`, which strips the channel prefix before templating to avoid a doubled `配置错误：配置错误: …`. The `state/` execution domain never imports i18n (WB-07.17 guard); dictionary copy lives in the pure display layer `taskText.ts`, and contracts locks the taxonomy with a six-row classification table plus bilingual template assertions.

### Data source and version markers (WB-03.16)

`lib/dataSource.ts` is the **single source of truth** for the source marker: `kernel` and `synthetic_demo`. The real run collection accepts only `kernel`, with three gates all inside the index code face — the **snapshot entry gate** (`snapshotRun` explicitly rejects `synthetic_demo` and defaults to `kernel`), the **index write gate** (`runsIndexFile` explicitly rejects demo entries and missing or invalid source markers, never silently correcting), and the **read gate** (`readRunsIndex` returns a readable error for demo entries and invalid values; entries from the v1 era that predate the field are inferred as `kernel` — demo data never had a path into the index, so absence-means-kernel is a factual inference, not a guess). The marker lands in `RunSnapshot.dataSource` and `RunIndexEntry.data_source` (passed through at submit registration), and the report export carries `machineJson({ data_source: 'kernel', … })`; demo-side exports (the candidates CSV column and the demo snapshot's `data-source` attribute) carry `synthetic_demo` themselves. Version markers keep their existing semantics: per-run `model_version` / `schema_version` / `seed`, the index's own `RUNS_INDEX_SCHEMA` (`'1'`; the new field is additive and old indexes stay readable), and the report's `meta.schema_version` (chapter 9). The analysis page keeps the real and demo channels mutually exclusive: the real run list filters out `demo` jobs, and the demo view requires an explicit source selection (`selection.source === 'synthetic_demo'`) with a source banner. The WB-03.16 structural guard in contracts locks the two marker values, `isDataSource` rejections, the demo project marker coming from the single source of truth, the run-collection and executor code faces importing nothing from the demo module, and the registration-chain / report / three-gate wiring.

### Real-run export binding (WB-09.01)

The export dialog has two mutually exclusive contexts: the demo context (exports the built-in sample, labeled `synthetic_demo`) and the real-run context (opened from the analysis page's real view). In the real context, scope counts and the exported artifact derive solely from the current run — the resolution rule (session-selected job → selector runId → newest real job) is provided by `currentRealJob` in `analysis/exportScope.ts` and shared by the analysis page and the dialog; scopes are all planned candidates / the analysis page's current filter (same overall-verdict rule) / the currently selected candidate, with actual counts shown (the selected option disables when empty, download disables with no candidates). The JSON artifact carries `data_source=kernel`, `run_id`, `spec`, `status`, `results` (index-aligned to the plan; candidates outside the chosen scope are absent from the artifact), `recommendation`, and an `export_scope` evidence block (scope/candidates/total; a partially returned run exports only its returned slots while the evidence still records the planned total); unrun drafts and demo data never enter it. Machine-output discipline (WB-11.19): numbers go through `machineJson` canonical decimals, locale-free; under both Chinese and English the machine column names (`<metric>.<stat>[scale]`), enumerations (pass / borderline / fail, kernel, run status), decimal point, and JSON schema key order are byte-identical (WB-09.09) — localized titles enter only the readable charts and reports (title/desc/svg annotations), never the machine columns or the envelope. The real context now offers JSON / CSV / SVG (CSV contract below; SVG under WB-09.05).

The real context's CSV (WB-09.02) exports `<run_id>-candidates.csv` with stable machine column names: `data_source / run_id / experiment_id` (empty cell when the run is unregistered, never fabricated) / `candidate_id` (content-addressed) / `candidate_index` / `replicates` / one column per parameter ID / `status` (ok|config_error|pending|failed|cancelled) / `fail_reason` / `verdict` (pass|borderline|fail, empty when unjudged); metric stat columns are `<metric>.mean|ci95_lo|ci95_hi|sd|n` with the scale in the column name (percent dimension `[ratio_0_1]` = kernel 0-1 ratio scale, never multiplied by 100 in export; amount dimension `[amount]`; `n` always `[count]`). The metric set = planned targets + actually produced metrics, scope-independent so column names stay stable. Unavailable stats = empty cells, never 0. Failure reasons are explicit: candidate-level = the kernel config_error text verbatim (commas/quotes go through RFC4180 quoting), run-level failure text lands on unrun rows. Numbers go through `machineNumber` canonical decimals, locale-free (column names identical in both languages); BOM + CRLF wrap the same as the demo CSV.

The real run's JSON snapshot (WB-09.04) carries explicit provenance and version in the envelope: `version` = `model_version` / `schema_version` (from the run's own analysis context, `null` when absent, never invented) + `plan_config_hash` (the plan's config hash) + `input_config_hash` (the input hash registered in the run index); `source` = `registered` (whether the run is registered) / `experiment_id` / `seed` / `created_at_unix` (all `null` when unregistered). The analysis toolbar's "download source JSON" and the export dialog both go through this one envelope (`scopedRunJson`) — the page no longer assembles it inline. Unrun drafts are saved separately as their own artifact `<run_id>-drafts.json`: three machine declarations — `data_source=candidate_draft`, `run_status=unrun`, `included_in_run_inputs=false` — guarantee that no downloaded draft can be mistaken for the run's input or output; each draft keeps its own `source_run_id` / `source_candidate_id`, baseline, full values and independent YAML edit buffer (snake_case, content untranslated), and a draft's presence or content never enters the run's JSON/CSV exports; the per-draft "plan and source JSON" carries the same declarations.

The SVG export (WB-09.05) serializes the analysis page's main chart for the current metric: the selected candidate's highlight rides along, chart styles and the white background are embedded in the file (a standalone copy keeps its appearance), and axis ticks plus metric/unit labels are preserved as rendered. Provenance rides the root node as `data-source=kernel`, `data-run=<run id>`, and `data-metric=<metric id>`; `xml:lang` and `data-locale` record the export language, and the title/desc state that data and verdicts come from the kernel, never recomputed by the frontend. The artifact is named `<run_id>-<metric>.svg`; when the analysis page has no main chart to serialize, nothing downloads and no success is reported. Demo and real SVG exports share one serializer (`svgSerialize`) — only the source, annotation, and data-run switch to the kernel side for real runs.

Archive and reopen (WB-09.07): when a real run terminates (succeeded / cancelled / failed), its machine snapshot lands in the project artifacts as `results/<run_id>.report.json` — the same `scopedRunJson` contract as the analysis-page export, with `spec` carrying the associated configs and the envelope bearing provenance and versions; the run index's `files` list stays in sync with present artifacts, and anything missing is still called out item by item by the audit. Saving the project writes the artifacts flat under `results/` plus the `results/runs.json` index; reopening an archive restores the run registry and present artifacts automatically (an unreadable index yields a readable error while the result files stay preserved byte-for-byte), and each present artifact in the project panel's run registry can be downloaded and re-exported.

Download semantics (WB-09.08): a success notice only appears after a real download lands — in the real context the CSV / JSON / SVG branches all notify on the line following `download(...)`, when the analysis page has no main chart to serialize the whole branch is skipped (no download, no success notice), and cancelling a file picker is not an error and reports no success; the desktop shell routes downloads through `on_download` into `~/Downloads` (name collisions get an `(n)` suffix and never overwrite a previous artifact, `Finished` reports the on-disk outcome explicitly, and the desktop destination has its own Rust test — the web side does not duplicate that). Every real-context artifact name starts with the run id (`<run_id>.json` / `<run_id>-candidates.csv` / `<run_id>-<metric>.svg` / `<run_id>-drafts.json`) — the traceability key is the run, never an invented timestamp.

## Equivalence acceptance

The roadmap's Phase 6 acceptance criterion: **the browser and the CLI, with the same configuration and the same seed, produce statistically equivalent results**. It is locked down by `crates/sandtable-cli/tests/web_parity.rs` — with the same configuration and the same seed, the report.json from the CLI's `simulate` and the results from the binding's `run_simulation_native` are **identical value by value** (not merely close in statistics; `serde_json` has `float_roundtrip` enabled, so an f64 written to disk and read back is bit-identical).

Scripting-layer Phase 1 (2026-10-11) closed the third edge: `crates/sandtable-python/tests/test_parity.py` locks py↔CLI with the same paradigm (simulate / sweep / recommend identical value by value, `days_csv` byte-for-byte identical to the CLI's `days.csv`) — the core is the single source of truth, and the pairwise equivalence loop over three independent thin forwardings (web_parity + py_parity + the desktop equivalence test) is complete.

The desktop command face and the wasm binding face also lock **parameter write-back and A/B statistics** into the same triangle (WB-03.17, 2026-10-20, two desktop tests): `param_writeback_parity_wasm_native` — over the same config (the Pokémon case), the full numeric read table is key-identical (including the lossless u64 channel), `param_apply` write-back (config_hash + read-back value) is value-identical, `kpi_availability` returns the same table, and the unknown-path rejection copy is verbatim-identical; `ab_stats_parity_wasm_native` — over the same pair of arm results, the desktop `ab_compare` and the wasm `ab_compare_native` Comparison is field-identical (verdict / CI / effect size), with the unknown-metric and seed-mismatch channels structurally identical and verbatim-identical copy. Same-config same-seed run output is separately locked by `run_wasm_parity_same_config_seed` (results / config_hash / days_csv).

## CI gates

All three jobs in `.github/workflows/ci.yml` cover the wasm surface:

- `test` job: the WASM compile gate (core, wasm32) + the WASM binding build gate (wasm-pack `--dev` produces pkg);
- `web` job: wasm-pack `--release` produces pkg → `npm ci` → `npm run build` (type check + bundling, asserting the artifacts contain .wasm) → **`node --test` frontend guards** (`tests/columns.test.mjs` column normalization including BigInt, `tests/presets.test.mjs` presets passing through the real wasm kernel, `tests/project.test.mjs` pack/unpack loop + path discipline + packed artifact passing through the real kernel; the latter two require pkg-node);
- `desktop-smoke` job (2026-10-13): wasm-pack `--target web --dev` produces pkg (the desktop shell inlines `web/dist` at compile time via custom-protocol, and tsc must resolve the file:pkg types as well) → frontend build → Xvfb brings the shell up headless and takes a screenshot for adjudication (startup-chain gate, recipe in `scripts/desktop_smoke.sh`).

The standalone workflow `.github/workflows/desktop-package.yml` (2026-10-13, manually triggered via `workflow_dispatch`): same wasm pkg + frontend artifact preconditions → `tauri-action` packages installable artifacts for three platforms (Windows msi+nsis / macOS dmg+app / Linux deb) and uploads them as artifacts — **no tags, no Release created**; unaccepted binaries never reach the Releases page (the version number is only ever supplied manually by the user). The frontend artifact is likewise produced first (custom-protocol inlining), so this pipeline incidentally also covers wasm type resolution and frontend bundling.

## Running locally

See [apps/web/README](https://github.com/cuihairu/sandtable/tree/main/apps/web): first `wasm-pack build crates/sandtable-wasm --target web`, then `npm install && npm run dev`.

To build the desktop installers locally: `cd apps/desktop/src-tauri && tauri build --features custom-protocol` (you need `apps/web/dist` ready first, see above); when verifying only the compilation chain, add `--bundles deb` to skip the AppImage download. For regenerating icons see [src-tauri/assets/README](https://github.com/cuihairu/sandtable/tree/main/apps/desktop/src-tauri/assets).
