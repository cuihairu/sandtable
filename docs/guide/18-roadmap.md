# Roadmap

## Method: Vertical Slicing

::: warning Why we dropped the "kernel first, game second" order
The original phasing had an inverted dependency: Phase 2 required "running the 30-day loop", but Metrics was scheduled for Phase 4 — without metrics the 30-day loop cannot be accepted. The more fundamental problem: **building the generic kernel first and the game second tends to skew the abstractions** (designing interfaces for an imaginary game).

Corrected to **vertical slicing**: first hardcode the minimal RPG into a runnable state (including the simplest metrics and one A/B comparison), verify the loop holds, then extract the generic kernel from the slice. Abstractions grow out of real code; they are not designed out of imagination.
:::

## Overview

```mermaid
flowchart LR
    P0["Phase 0<br>Definition (this document)"] --> P1["Phase 1<br>Minimal closed loop<br>(vertical slice)"]
    P1 --> P2["Phase 2<br>Kernel extraction and config-driven loading"]
    P2 --> P3["Phase 3<br>Experiment layer + analysis layer"]
    P3 --> P4["Phase 4<br>Sensitivity and recommendation"]
    P4 --> P5["Phase 5<br>Reports and real-config validation"]
    P5 --> P6["Phase 6<br>Web (WASM + React)"]
    P6 --> P7["Phase 7<br>Desktop (Tauri 2)"]
    P7 --> FU["Later<br>Optimization / scripting / bindings"]
```

::: tip Platform discipline
Web and Desktop are scheduled for Phase 6 / 7, **but their architectural preconditions are enforced by CI gates from Phase 1 on**: core must compile for `wasm32-unknown-unknown`, core's dependency tree must contain no platform libraries, and parallelism must be able to degrade to serial (see [simulation kernel](./04-kernel.md)). Features come later; boundaries do not.
:::

## Phase 0 — Definition (complete)

Core concepts, time model, RNG, metric formulas, constraint adjudication, and the roadmap are all written down (i.e., this site).

## Phase 1 — Minimal Closed Loop (Vertical Slice)

**Do**: hardcode the minimal RPG ([MVP definition](./16-mvp.md)): Actor probabilistic behavior + analytic combat + reward + progression + churn mechanics; advance 30 days day by day; the minimal implementation of the [metric formula set](./13-kpi-metrics.md) (WinRate / Power distribution / gold and inflation / retention and churn); CLI `simulate` + `compare`; one A/B report of attack=100 vs 105.

**Platform gates (in CI from this phase)**:
- `cargo check --target wasm32-unknown-unknown` passes (core pulls in no platform dependency);
- Output schema designed against the Arrow contract (column names / types map directly to RecordBatch, see [data output](./09-data-output.md)).

**Verify**:
- Deterministic snapshot: same seed, rerun, bit-for-bit identical;
- Analytic cross-check: closed-form expected damage and independent expected reward match the simulation mean ([testing strategy](./19-testing.md));
- All seven MVP acceptance items ([MVP](./16-mvp.md)) pass.

**Accept**: all seven items above met → MVP holds.

## Phase 2 — Kernel Extraction and Configuration-Driven Loading

**Do**: extract the generic World / event queue / Clock / keyed RNG / online-aggregation metrics from the slice; introduce YAML configuration (Model and Scenario separated), the parameter registry, config_hash, schema_version, and the formula engine (compiled at load time); parameterize Cohorts; move the built-in systems into the `systems` module with behavior unchanged; provide Arrow / Parquet export as a feature (the MVP's JSON + CSV stay the default).

**Accept**:
- After extraction, the same experiment's results are **bit-for-bit identical** to Phase 1 (refactor changes no behavior);
- The same YAML keeps config_hash unchanged after key reordering and added comments;
- The same experiment runs by changing config, not code.

## Phase 3 — Experiment Layer + Analysis Layer

**Do**: Grid / Random sweeps, replicates orchestration, candidate parallelism (rayon), the `sweep` subcommand, confidence-interval-based constraint adjudication, and comparison reports; **DuckDB analysis layer (native)**: duckdb-rs reads the result datasets (Parquet / CSV) for after-the-fact SQL exploration (per-cohort power, economic income/expense, etc.), never entering the simulation path.

**Accept**: after changing a parameter range, candidate experiments are auto-generated and compared; constraint adjudication outputs the three states PASS / BORDERLINE / FAIL (see [metrics](./13-kpi-metrics.md)).

## Phase 4 — Sensitivity and Recommendation

**Do**: OAT elasticity (extracted from grid data), single-parameter-axis interpolation recommendation intervals, Confidence criteria, and the `recommend` output.

**Accept**: parameter intervals with confidence can be derived from experiment results rather than raw data alone; interval endpoints are traceable to the interpolation process.

## Phase 5 — Reports and Real-Config Validation

**Do**: HTML reports (charts, KPIs, parameter comparison); **real-config validation node** — take a real or publicly documented game's numeric configuration and run it through the whole pipeline; evaluate Excel / CSV config import.

**Accept**: an external configuration (not the minimal RPG) runs end to end through simulate → sweep → recommend, exposing and fixing real integration friction. **Done**: the Pokémon (Gen 1 Kanto) case is integrated, the whole chain runs with zero model changes; the friction list and follow-up candidates are in [real-config validation](./21-pokemon-case.md); CSV import landed as `params export / import` (see [CLI](./10-cli.md)).

## Phase 6 — Web (WASM + React)

**Do**: `sandtable-wasm` thin bindings (run_simulation / validate_config, no simulation logic inside); React + TS + Vite frontend; DuckDB-Wasm local analysis; "Try in your browser" — open the page, import a [project file](./09-data-output.md) or config, run a small-to-medium simulation locally, and charts appear directly, zero install.

**Progress**: the bindings, frontend skeleton, and DuckDB-Wasm query panel have landed (config editing → local simulation → KPI / per-day curves / cohort table → SQL query with chart output, equivalence locked by tests, see [Web](./22-web.md)); result export has landed (`days.csv` / `report.json` downloads, isomorphic with the CLI `simulate --out` artifacts); frontend sweeping has landed (single-axis grid sweep + constraint adjudication table + recommendation band visualization, JS drives candidate by candidate, executed locally within the budget gate).

**Boundaries**: Web only promises small-to-medium simulations (DuckDB-Wasm is single-threaded by default, WASM memory is capped at 4GB); large sweeps with ten-thousand-scale players are steered toward the CLI / Desktop.

**Accept**: browser and CLI with the same config and same seed produce statistically equivalent results ([testing strategy](./19-testing.md)); results can be queried and charted via DuckDB-Wasm. **Done**: equivalence is locked value-by-value by the `web_parity` test, and the DuckDB-Wasm query panel has landed — see [Web](./22-web.md).

## Phase 7 — Desktop (Tauri 2)

**Do**: a Tauri 2 shell (React UI + Rust backend), native simulation + native DuckDB + local files; the primary form factor for Windows and similar platforms, with no Node / Python backend.

**Accept**: the desktop client runs the full experiment flow equivalently to the CLI; installers are usable on Windows / macOS.

**Dependency assessment (2026-10-10: green to start, no dependency blockers) → decision to start made (2026-10-10)**:

- **Technical side**: Tauri 2.x is the current stable line (stable since 2024-10, still actively maintained in 2026; the updater plugin requires Rust 1.90+); the architecture matches this section's charter — the `apps/desktop` shell (see the shell placement convention in [project structure](./17-project-structure.md)) + `sandtable-core` connected directly as a path dependency (native simulation, no wasm boundary) + `duckdb-rs` reading Parquet/CSV (the same dependency as the Phase 6 native analysis layer) + reusing apps/web's React 19 + Vite 8 frontend (Tauri natively supports Vite build artifacts).
