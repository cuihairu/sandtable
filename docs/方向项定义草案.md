## 1. CI Balance Regression

### 1.1 Current Coverage

- **Golden snapshot**: default-config metrics byte-for-byte + `config_hash` (core tests) — any kernel behavior change turns CI red;
- **Case gradient**: `crates/sandtable-cli/tests/cases.rs` Pokémon tiered gradient (monotonicity / tiering assertions);
- **Closed-form comparison**: closed-form reconciliation of pity draw expectations (chapter 24);
- All of the above run in CI via `cargo test --workspace`.

Conclusion: "kernel behavior changes → CI red" is covered; what is missing is "**balance level** changes → CI red".

### 1.2 Gap

When case values (`examples/pokemon.yaml` etc.) are edited, there is no CI assertion on the absolute KPI levels (churn_rate / retention_d7 / win_rate) — only manual review remains as the safety net. The golden snapshot anchors the default config, not case configs.

### 1.3 Options

| Option | Approach | Cost | Verdict |
| --- | --- | --- | --- |
| A. Keep status quo | Golden snapshot + gradient tests; level drift left to review | Zero | Acceptable, but the safety net is human |
| **B. Case KPI level assertions (recommended)** | Add narrow-band assertions on the pokemon.yaml 30-day baseline (churn_rate band, retention_d7 floor, etc.; thresholds from the chapter 21 recorded baseline ± tolerance); editing case values must update the assertions in the same change | One test file; no CI duration change | Turns balance drift from a manual net into CI interception; the cheapest real gap to close |
| C. Standalone balance regression job | CI runs the full case set, compares KPI reports against baseline files | New CI job; high duration and maintenance cost | Marginal benefit; not recommended |

### 1.4 Decision Points (decided, see §4)

1. Do it at all (B vs. stay with A);
2. Threshold tightness (suggestion: chapter 21 recorded baseline ±10%, or a statistical CI widening);
3. Whether to also anchor the gacha-pity case (E[T] already has closed-form reconciliation; marginal).

## 2. Visualization System Graph & Designer Workflow

### 2.1 Current Coverage

- System semantics are scattered: kernel (04) / config & formulas (07) / sweep (12) / recommendation (15) / case study (21); no single panoramic graph;
- Formula curves already have a **program-generated** precedent: `formula_curves.rs` samples the real evaluator to produce SVGs (chapter 25) — the established discipline that keeps docs and implementation from drifting;
- The designer path (edit YAML → simulate → sweep → recommend → report) is spread across chapters 10/12/15/21 with no one-page tour.

### 2.2 Gap

- A new reader cannot see "which Systems live in the simulation loop and how data flows" on one page;
- "I want to change one number and verify the impact" requires stitching the path across four chapters.

### 2.3 Options

| Option | Approach | Cost | Verdict |
| --- | --- | --- | --- |
| **A. Program-generated system graph (recommended)** | Add a core example (e.g. `system_graph.rs`) that outputs the graph from the live System registry (subscribed events / data flow) → SVG lands in `docs/assets/`, referenced by chapter 04 | One example; hand-drawn SVGs inevitably drift, program generation follows the formula_curves discipline | Recommended |
| **B. One-page designer workflow (recommended)** | A five-step tour "from changing a number to verifying impact", no new chapter — merged into an existing one (02 or 21), linking existing chapters | Half a page | Recommended |
| C. Interactive system graph | Render the system graph in the web app | Frontend effort | On demand; not now |

### 2.4 Decision Points (decided, see §4)

1. How the graph is produced (program-generated vs. hand-drawn SVG);
2. Graph information density (System names + subscribed events only / including data-flow arrows);
3. Where the designer workflow lands (02 / 21 / a new chapter 26).
